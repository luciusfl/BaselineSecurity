# Windows 11 Security Baseline - System Design

This document describes how the Security Baseline suite is built, installed and run, and how its parts work together. It covers the architecture, the installation flow, the privilege model, where files are written, and how remediation and rollback work.

It does not list the individual security checks. The full list of settings, expected states, CIS references, and which checks are audit-only (not configured by Remediations.ps1) is in SecurityBaselineSettings.html. That file is the reference for what is checked. This document covers how the suite works.

This file uses only basic Markdown (headings, lists, bold, italic) so that it displays correctly in the formatted view of Windows Notepad.

The code was security scanned using Anthropic's Fable 5.2 model at the Max setting.

The source code is available at https://github.com/luciusfl/BaselineSecurity

## 1. Purpose and scope

The suite keeps a **stand-alone Windows 11 PC** (not domain-joined, no Intune or corporate Group Policy) aligned with a hardened security baseline. The baseline combines a curated set of settings with selected automated Level 1 recommendations from the CIS Microsoft Windows 11 Stand-alone Benchmark v5.0.0.

It has three jobs:

- **Detect** drift from the baseline, continuously. Done by Audit.ps1, which runs as a scheduled task. It is read-only: it changes no settings, and the only files it writes or deletes are its own logs and temporary files.
- **Fix** non-compliant settings, on demand. Done by Remediations.ps1. It changes settings and records undo state for every change.
- **Undo** what remediation changed. Done by the generated rollback.ps1, which restores the recorded original state.

A small native notifier, WatchDog.exe, shows a Windows notification (toast) when the scheduled audit finds a problem. A person decides whether the drift was intentional before reverting it.

## 2. Components

### 2.1 Source repository

- **Audit.ps1** - Audit engine. Evaluates every baseline check, writes logs, and exits with 0 (secure) or 1 (insecure).
- **Audit.cmd** - Wrapper for interactive use. Runs with or without elevation (see section 6) and starts Audit.ps1 with -NoProfile -ExecutionPolicy Bypass. Passes arguments through. Audit.cmd ?, -?, /?, help and -help show the options (Audit.ps1 -Help); they are checked in Audit.cmd, because PowerShell takes -? for its own help, and Audit.ps1 also treats ? and help given in place of RestrictTo as a request for help. Nothing is checked and no log file is written.
- **Remediations.ps1** - Remediation engine. Idempotently brings non-compliant settings to the baseline and records undo state for every change. Also contains the Invoke-Rollback function that becomes rollback.ps1.
- **Remediations.cmd** - Elevation-checking wrapper for Remediations.ps1. Remediations.cmd -RestrictTo Edge,OS (or RestrictTo=Edge,OS) applies only the listed systems, OS, Edge and Chrome, with the same rules as Audit.ps1 -RestrictTo (section 7): unknown names are ignored with a warning, and without it everything is applied. cmd.exe splits arguments at commas and equal signs, so Remediations.cmd collects the names after RestrictTo and passes them on as one list. In Remediations.ps1 the OS settings sit in three blocks guarded by Test-SystemSelected 'OS'; the functions the browser settings need are defined outside them. The rollback snapshot keeps working: settings that a restricted run skips are recorded the first time a later run checks them. Remediations.cmd ?, -?, /?, help and -help show the help (checked before the elevation check, so it works unelevated and changes nothing). Remediations.cmd Analyze lists the snapshot as "original -> now" lines (section 9.3). The options are not case sensitive.
- **Rollback.cmd** - Elevation-checking wrapper for the generated %ProgramData%\SecurityBaseline\rollback.ps1. It takes that folder from Windows, not from the %ProgramData% environment variable (see section 11). Prints "Nothing to roll back" if no rollback.ps1 exists.
- **InstallTasks.ps1** - Installer. Copies the files the tasks run to %ProgramFiles%\SecurityAudit, registers the toast identity and the two scheduled tasks, then starts the first audit. The audit task runs as LocalService by default, or as SYSTEM with -RunAuditElevated (see section 5.2).
- **Install.cmd** - Elevation-checking wrapper for InstallTasks.ps1. Passes its arguments through, so Install.cmd -RunAuditElevated works. Install.cmd ?, -?, help (and /?) show the supported parameters, the installation folder and the log folder; this is checked before the elevation check, so the help also works from an unelevated prompt, and it installs nothing.
- **WatchDog folder** - C# source (Program.cs, WatchDog.csproj) for WatchDog.exe, the toast notifier.
- **SecurityBaselineSettings.html** - The baseline reference: every setting, its expected state, how it is checked, and whether it is audit-only.
- **Design.md** - This document.
- **CIS_Microsoft_Windows_11_Stand-alone_Benchmark_v5.0.0.pdf** - The CIS benchmark the baseline follows. SecurityBaselineSettings.html links to the page of each CIS recommendation ("CIS PDF" links, for example file.pdf#page=239), so the PDF must stay next to it. Edge and Chrome open these links at the right page.
- **CIS_Microsoft_Windows_11_Stand-alone_Benchmark_v5.0.0.json** - Every recommendation of the CIS benchmark as structured data (ID, title, profile level, Automated or Manual, page, expected state, registry locations with parsed expected values, Group Policy path or command, and the full text of every section: description, rationale, impact, audit, remediation, default value, additional information, references and the CIS Controls mapping with implementation groups). Text sections keep the paragraphs and list items of the PDF, one per line. It is generated from the PDF, so the PDF never has to be parsed again; use it to compare the baseline with the benchmark. It stays in the repository and is not deployed: Update-AuditCheckDetails.ps1 copies the description and rationale that Audit.ps1 needs from it into AuditCheckDetails.json. Its header records which independent checks passed when it was generated and which pdftotext produced the text. It depends on the PDF alone: the comparison with Audit.ps1 and Remediations.ps1 is printed when it is generated, not stored, so the file does not change when the scripts do.
- **CIS_Microsoft_Edge_Benchmark_v5.0.1.pdf** and **CIS_Microsoft_Edge_Benchmark_v5.0.1.json** - The CIS Microsoft Edge Benchmark (147 recommendations) and the same structured data generated from it, as a reference for browser settings. The baseline does not follow this benchmark yet: Audit.ps1 and Remediations.ps1 refer only to the Windows benchmark by CIS number, so nothing reads the Edge JSON, and its numbers (for example 1.2.1) overlap with Windows numbers. Five recommendations (1.4.1, 1.78, 1.85, 1.131, 3.3.1) have a parser warning, because their Audit text uses wording the parser does not read ("in effect when the following registry value does not exist" and "any REG_DWORD value except 0"); their registry locations are still listed.
- **CIS_Google_Chrome_Group_Policy_Benchmark_v1.1.1.pdf** and **CIS_Google_Chrome_Group_Policy_Benchmark_v1.1.1.json** - The CIS Google Chrome Group Policy Benchmark (140 recommendations, 102 Level 1 and 38 Level 2) and the structured data generated from it, as a reference for Chrome settings. It is the Chrome benchmark that fits this baseline: its Audit sections name the registry values under HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Google\Chrome that Chrome also reads on a stand-alone PC. The CIS Google Chrome Enterprise Core Browser Benchmark is audited in the Google Admin console instead (almost no registry paths), and the old CIS Google Chrome Benchmark v3.0.0 is archived. Like the Edge benchmark, it is written for managed PCs (Active Directory domain members), so only clear security problems are taken from it (seven Chrome policy checks, section 7.3), and nothing reads the JSON yet. Where the benchmark and Google's own policy definitions disagree, Google's definitions are followed (CIS 2.11.1, section 7.3). The PDF names no data type ("registry location which should be set to 0"), so its registry entries have valueType null and expectedText "should be set to ..."; the type comes from Google's Chrome policy list (linked in the references of each recommendation) when a setting is adopted. List policies (lists of sites or domains, for example ClipboardAllowedForUrls) are one registry entry for the list key, with listValues true and the example values the PDF prints (ClipboardAllowedForUrls\1 = https://www.example.com) in examples; where the PDF prints no colon before the value name but expects a single value (2.7.2), the last part of the path is taken as the value name and the entry has valueNameInferred true. 28 recommendations carry parser warnings, mostly list policies, whose Audit text has no value sentence, and titles that state their expected state in a form the parser does not read ("Is 'Enabled' to 'Deny Permissions'"); 5 titles name the policy slightly differently from its Group Policy path, which is recorded as a warning for that recommendation.
- **Export-CisBenchmarkJson.ps1** - Generates these JSON files from the PDFs. It supports the CIS benchmarks listed in $script:BenchmarkProfiles in the script, chosen by the PDF file name, and refuses any other PDF, because its layout has not been checked (for example the archived CIS Google Chrome Benchmark v3.0.0 or the Enterprise Core benchmark). A profile sets what differs: the registry wrap width (77 characters in the Windows PDF, 83 in the Edge PDF, 82 in the Chrome PDF), whether the table of contents is read from "pdftotext -raw" (Chrome: the -layout text breaks its page numbers apart), whether the heading starts with the level ("2.1.1 (L2) Ensure ...", Chrome), and whether the benchmark is the one the baseline follows; only for the Windows benchmark are the Microsoft documentation confirmations used and the registry values cross-checked against Audit.ps1 and Remediations.ps1. Run it with -PdfPath for the Edge or Chrome PDF; without it, it rebuilds the Windows JSON. Run it again with the new PDF for the next benchmark version (it needs pdftotext.exe, which is part of Git for Windows as the Xpdf version, or text already extracted with "pdftotext -layout -enc UTF-8" and "pdftotext -table -enc UTF-8"; the -table text is used only for the CIS Controls tables, because only it prints each implementation group circle on its own row). It stops without writing a file if any of its checks fails: the recommendations in the table of contents, the body and the appendix summary table must agree; every registry location and every text field must consist of characters printed in that recommendation; every parsed expected-value rule must rebuild into the sentence as printed; the expected values must carry the printed data type (numbers for REG_DWORD, strings for REG_SZ and REG_MULTI_SZ); every Group Policy path must end with the setting it names; every exported text section must be the whole section as printed, not a part of it; no hyphen at a line end may look like a split word (a word printed elsewhere without the hyphen); registry lines must stay within the wrap width of the benchmark and must not continue past a page break; the CIS Controls rows read from the -table text must match the -layout text, circles included; and no page footers or broken hyphenated words may remain. A mutation test (deliberately breaking the parser in seven ways) confirmed that each check stops the run. Where the PDF states a registry data type ambiguously or wrongly (18.4.3 and 2.3.10.8), the script records what Microsoft's own documentation says (field microsoftDocumentation, with the source link and the date it was checked); these confirmations are kept in the script, and it stops if one no longer matches an entry, so they are reviewed again for a new benchmark version. For the Windows benchmark it also prints the differences between the benchmark and the registry values used by Audit.ps1 and Remediations.ps1.
- **AuditCheckDetails.json** - Description and security rationale for every audit check, which Audit.ps1 prints under each failed check (see section 7.5). It is the only details file that is deployed, and Audit.ps1 reads no other. It has two parts:
  - **checks** (written by hand) - the checks whose name does not start with a CIS number. A check that covers CIS recommendations only lists their IDs (cisIds), and its text then comes from cisRecommendations in the same file. The other checks have their own text with source links (Microsoft Learn, Microsoft Support, MITRE ATT&CK, IETF RFCs, Chrome Enterprise) and the date the sources were read. An empty rationale means no trustworthy source stating the security reason was found. The names must match the check names in Audit.ps1 exactly; a renamed check needs its entry renamed too.
  - **cisBenchmark** and **cisRecommendations** (generated, must stay the last two properties) - a copy of the ID, title, printed page, description and rationale from the CIS benchmark JSON for every recommendation Audit.ps1 checks. Checks named "CIS <id> ..." and cisIds entries take their text from here. Do not edit this part by hand; run Update-AuditCheckDetails.ps1.
- **Update-AuditCheckDetails.ps1** - Writes cisBenchmark and cisRecommendations in AuditCheckDetails.json from the CIS benchmark JSON and leaves everything before them unchanged. It copies the recommendations whose CIS number appears in the code of Audit.ps1 (check names "CIS <id> ..." and the Recommendation, Id, SizeId and RetentionId values of its tables; comments are ignored) plus every cisIds entry, and it stops without writing if one of them is not in the benchmark JSON. Run it after adding or removing a CIS check in Audit.ps1, after changing cisIds, and after regenerating the benchmark JSON. A second run changes nothing. It is not deployed.
- **.vscode\tasks.json** - Build task "WatchDog: publish and stage", which builds WatchDog.exe and stages all deployable files into the publish folder.
- **CIS_Microsoft_Windows_11_Stand-alone_Benchmark_v5.0.0.pdf** - The CIS benchmark the CIS-numbered checks come from.
- **AGENTS.md** - Rules for keeping scripts and documentation aligned.

rollback.ps1, the publish folder, and the WatchDog bin and obj folders are generated and are excluded by .gitignore.

### 2.2 Wrapper scripts (the .cmd files)

Every .cmd wrapper except Audit.cmd checks for elevation the same way. It runs %SystemRoot%\System32\fltmc.exe with its output discarded. If that fails, the wrapper prints "Error. [name].cmd must run elevated." and exits with code 1. Install.cmd first looks for a help argument (?, -?, help or /?) and shows the help without the elevation check.

fltmc.exe (the filter manager control program) fails for any token that is not elevated, so this is a reliable elevation test that needs nothing else installed.

The wrappers then call Windows PowerShell 5.1 with two options:

- **-NoProfile**, so user profile scripts cannot change behavior.
- **-ExecutionPolicy Bypass**, so the scripts run on a machine whose execution policy blocks unsigned scripts, without changing that policy permanently.

They return the script's exit code.

### 2.3 WatchDog.exe

WatchDog.exe is a tiny .NET 10 Windows program with no console window. It is published **self-contained and Native AOT** for win-x64, so it needs no .NET runtime on the target machine. Its logic is:

1. Check that the last audit finished. Audit.ps1 ends SecurityAudit.log with its summary line ("Checks run: ..."), so a log without it belongs to a run that was stopped (the task's 45-minute limit, section 5.2) or failed:
    - If an audit still has SecurityAudit.log open for writing, exit with 0 silently. This happens when the task's run stopped at once because an elevated Audit.cmd was running (exit code 3); the result is not known yet. WatchDog detects the writer by opening the log for reading while allowing only other readers, which fails exactly while a writer has it open. Only SYSTEM, Administrators and the audit task can write the log, so no other program can make a run look unfinished or still running, and a program that only reads the log does not change the result.
    - If the log is missing or has no summary line, but the audit task is running right now, exit with 0 silently. A newer run has started and replaces the older result, and its own end triggers WatchDog again. This matters when that run has not yet opened its log: starting PowerShell can take a minute or more, for example right after a laptop wakes from standby, and the log still holds the older run, which may be unfinished because standby made it exceed the 45-minute limit. WatchDog asks Task Scheduler's history (Microsoft-Windows-TaskScheduler/Operational, the log its own trigger listens to) for the newest "started" (100) or "finished" (102) event of the audit task in the last 7 days; a start means the task is running. The Event Log service filters the events itself and WatchDog reads only the newest match, so the query takes a few milliseconds (under 0.1 s even when it has to search the whole history, which Windows caps at 10 MB). If the history cannot be read, WatchDog reports the log as below. A run started within milliseconds of WatchDog can still be missed; that rare case shows the toast as before.
    - If SecurityAudit.log does not exist, show a toast "The last security audit wrote no log", whose link opens the log folder.
    - If the summary line is missing, show a toast "The last security audit did not finish", followed by the failures found until then (if any), whose link opens SecurityAudit.log, which shows the last check the audit reached.

    Task Scheduler logs event 102 also for a run it stops at the time limit (tested with a 1-minute limit: event 329 "terminated", then 102), so WatchDog runs after such a run too.
2. If the audit finished and %ProgramData%\SecurityAudit\SecurityAuditErrors.log does not exist, exit with 0 silently (the last audit passed).
3. Otherwise read the file and show a **high-priority toast** titled "Security Configuration Alert" with the failure text, using the AppUserModelID "Security Configuration Alert". The toast uses duration="long", so the banner stays on screen for about 25 seconds instead of 5. Afterwards it stays in Notification Center (Win+N) until dismissed or until Windows expires it (about 3 days). Clicking the toast, or its **Open log** button, opens SecurityAuditErrors.log in the default app for .log files through a file:/// link. The link points to the current file, not a copy: an older toast opens the latest results, and Windows reports that the file cannot be found if the latest audit passed.
4. If anything fails, write the exception to its log and exit with 1.

Every run writes one line to %LOCALAPPDATA%\SecurityAudit\WatchDog.log of the signed-in user: what WatchDog found and what it did, for example "audit log unfinished (last written 2026-11-21 04:04:44); audit task running; no toast", or its error. The log is in the user's own folder because WatchDog runs as that user and may only read the audit log folder. Above 1 MB it is renamed to WatchDog.old.log (replacing the previous one), so the two files stay at about 2 MB. A failure to write it never stops WatchDog. It is a troubleshooting aid only: any program running as the user can change or delete it, and nothing reads it back, so it cannot affect whether a toast is shown (that depends only on the audit logs, which only SYSTEM, Administrators and the audit task can write, and on Task Scheduler's history).

WatchDog is a separate native program, not a PowerShell script, for two reasons:

- **Toasts must appear in the user's interactive session.** The audit runs as LocalService (or SYSTEM) in session 0, which has no desktop and cannot show notifications. The notifier has to run as the signed-in user.
- **No console flash.** A Windows program without a console shows no window, unlike powershell.exe -WindowStyle Hidden, which can briefly show a console.

## 3. Requirements

- **Operating system:** Windows 11 or later (build 22000 or later); Install.cmd refuses to install on Windows 10. Some checks change behavior by build number, for example 22H2 (build 22621) and later.
- **Machine type:** A stand-alone personal computer: unmanaged, not domain-joined, no corporate Group Policy. Domain or MDM policy would conflict with local remediation.
- **PowerShell:** The minimum is Windows PowerShell **5.1** (powershell.exe), which ships with Windows 10 and 11. Audit.ps1, InstallTasks.ps1 and the generated rollback.ps1 declare "#requires -Version 5.1". Remediations.ps1 has no #requires line, but Remediations.cmd always starts it with powershell.exe. The .cmd wrappers and the audit scheduled task always call powershell.exe, never pwsh.exe, so PowerShell 7 is not required or used even if it is installed. The scripts have not been tested under PowerShell 7.
- **Privileges:** An administrator account and an **elevated** prompt for Remediations.cmd, Rollback.cmd and Install.cmd. Audit.cmd also runs unelevated, but then skips the checks that need administrator rights. See section 6.
- **Notifications:** Windows notifications must be on (Settings > System > Notifications), or the toast is suppressed.
- **Build machine only:** The .NET 10 SDK with the Native AOT prerequisites (MSVC build tools) to publish WatchDog.exe. The target machine does not need the SDK.
- **Optional:** Microsoft Edge and/or Google Chrome. Browser policies apply only to browsers that are installed (see section 7.3).

## 4. Build and packaging

The deployable set is produced by the VS Code default build task **"WatchDog: publish and stage"** (in .vscode\tasks.json), which runs three steps in order:

1. Runs "dotnet publish WatchDog\WatchDog.csproj --configuration Release". This produces WatchDog\bin\WatchDog.exe (self-contained, AOT, symbols stripped).
2. Creates the publish folder if it is missing.
3. Copies the deployable files into the publish folder: Readme.md, Design.md, Audit.ps1, Audit.cmd, InstallTasks.ps1, Remediations.ps1, Remediations.cmd, Rollback.cmd, Install.cmd, SecurityBaselineSettings.html, CIS_Microsoft_Windows_11_Stand-alone_Benchmark_v5.0.0.pdf, AuditCheckDetails.json and WatchDog.exe. The CIS benchmark JSON, Export-CisBenchmarkJson.ps1 and Update-AuditCheckDetails.ps1 are development files and are not copied. The copy step does not delete files, so a CIS benchmark JSON left in the publish folder by an earlier build stays there until it is deleted; Audit.ps1 no longer reads it.

The steps run in sequence, so if the build step fails, nothing is copied.

To deploy, run Install.cmd (elevated) from the publish folder, or from any copy of it. InstallTasks.ps1 copies Audit.ps1, AuditCheckDetails.json and WatchDog.exe from its own folder to **%ProgramFiles%\SecurityAudit** and registers the scheduled tasks with the full paths of those copies. The tasks never run files from the folder the installer was started from, which may be writable by the signed-in user (for example the publish folder in the user profile). After a new build, run Install.cmd again so the copies are replaced; the folder you deployed from can then be moved or deleted without breaking the tasks.

## 5. Installation

### 5.1 Recommended operator workflow

1. Run **Audit.cmd** (elevated, for the complete result) to see the current compliance state. Nothing is changed.
2. Run **Remediations.cmd** (elevated) to fix non-compliant settings. It writes rollback state. Restart or sign out if it asks you to.
3. Run **Audit.cmd** (elevated) again. Repeat steps 2 and 3 until no failures remain, or until the remaining failures are audit-only items you have reviewed and fixed by hand.
4. Run **Install.cmd** (elevated) to register the scheduled tasks for continuous monitoring. By default the hourly audit runs as LocalService and skips the checks that need administrator rights; run **Install.cmd -RunAuditElevated** to have it run every check as SYSTEM (see section 5.2, step 5).

The tasks are installed **last** on purpose. If they were installed on a non-compliant machine, every hourly run would raise a toast for findings the operator already knows about.

### 5.2 What Install.cmd and InstallTasks.ps1 do

InstallTasks.ps1 takes two optional switches, **-RunAuditElevated** and **-Uninstall** (Install.cmd passes them through; they cannot be combined, see section 5.5). Before anything else it refuses to install on a Windows version older than Windows 11 (build 22000): it reads the build number from the operating system, and if that cannot be read the installation is refused too, so Windows 10 never gets the tasks. Nothing is changed in that case and the exit code is 1. Its -Help switch, which Install.cmd uses for ?, -?, help and /?, only prints the parameters, the installation folder, the log folder and the task names, then exits without changing anything. It runs these steps in order and stops at the first error. An unknown argument also stops it, so a mistyped switch cannot silently install the default mode.

**Step 1. Check prerequisites.** Audit.ps1, AuditCheckDetails.json and WatchDog.exe must be in the same folder as the installer.

**Step 2. Copy the files to %ProgramFiles%\SecurityAudit** and protect them. A reinstall first stops a running audit or watchdog task (and a WatchDog.exe that runs from the installation folder), because the audit keeps SecurityAudit.log open for its whole run and a running WatchDog.exe cannot be overwritten; the tasks are registered again in steps 5 and 6. Without this, a reinstall during an audit failed with "The process cannot access the file ... SecurityAudit.log". Copying the files retries for up to 15 seconds and ends WatchDog.exe again if the watchdog task started it in the meantime (the second error seen: "The process cannot access the file ... WatchDog.exe"). Deleting the old logs in step 3 also retries for up to 15 seconds, and if a file stays open (for example by a running Audit.cmd) the message says so. The folder gets its own access list without inheritance: SYSTEM and Administrators full control, Users read and execute (WatchDog runs as the signed-in user), and, in the default LocalService mode, read and execute for the audit task's SID (see step 5). Every copied file is reset to inherit only these permissions, because copying over an existing file would keep that file's own access entries. Nobody but SYSTEM and Administrators can change what the tasks run. If the installer is started from that folder itself, nothing is copied and only the permissions are set.

**Step 3. Create the log folder** %ProgramData%\SecurityAudit (normally C:\ProgramData\SecurityAudit) and protect it. ProgramData lets ordinary users create files in new subfolders, which would let any user plant a fake SecurityAuditErrors.log that WatchDog then shows. The installer therefore gives the folder its own access list without inheritance: SYSTEM and Administrators full control, Users read only (WatchDog runs as the signed-in user and reads the log), and, in the default LocalService mode, modify for the audit task's SID, so the task can replace its logs. Other LocalService processes cannot write there. A read-only entry for OWNER RIGHTS (S-1-3-4) takes away the right that the owner of a file otherwise always has, to change the file's permissions: the logs the task creates are owned by LocalService, so without it any other LocalService process could take them over. The logs of the previous audit (SecurityAudit.log and SecurityAuditErrors.log) are deleted, because they may belong to the other task account, and so is the SecurityAudit.lock file that earlier versions used, and any other file in the folder that is not owned by SYSTEM or Administrators is deleted too; the audit started in step 7 writes fresh logs.

**Step 4. Register the toast identity.** Windows only delivers toasts from a desktop app whose AppUserModelID is attached to a Start Menu shortcut. The installer:

- creates the shortcut "Security Configuration Alert.lnk" in %APPDATA%\Microsoft\Windows\Start Menu\Programs, pointing to WatchDog.exe, and
- sets the shortcut's System.AppUserModel.ID property to "Security Configuration Alert". It does this through the Windows property store API, using a small inline C# type, because PowerShell has no built-in command for it.

The shortcut goes in the **installing user's** Start Menu. That is why the installer must run from that user's elevated session, not from a different admin account.

**Step 5. Register the task "Security Configuration Audit".**

- Runs as, by default: **LocalService** (S-1-5-19), not elevated (least privilege). The checks that need administrator rights (section 6.1) are skipped and logged as [ELEVATION REQUIRED]; they do not count as failures, so they never raise a toast. Two Task Scheduler options limit the account further:
  - ProcessTokenSidType Unrestricted adds the task SID NT TASK\Security Configuration Audit (S-1-5-87-4287945998-81494110-2375371360-1575562353-864530297, computed from the task name; schtasks /showsid /tn "Security Configuration Audit" shows it) to the process token. The install and log folders grant access to this SID, not to LocalService, so no other LocalService process gets it.
  - RequiredPrivileges keeps only SeChangeNotifyPrivilege (needed to traverse folders). LocalService normally also holds SeImpersonatePrivilege and other privileges; SeImpersonatePrivilege in particular is the usual path from a compromised LocalService process to SYSTEM.
- Runs as, with **-RunAuditElevated**: **SYSTEM** (service account), with the highest available privileges. Audit.ps1 gets -RunAuditElevated too, so every check runs, and one that cannot run counts as a failure.
- Action: powershell.exe -NoProfile -NonInteractive -WindowStyle Hidden -ExecutionPolicy Bypass -File "%ProgramFiles%\SecurityAudit\Audit.ps1", followed by -RunAuditElevated in the elevated mode.
- Trigger: one time trigger that starts at the installation time and repeats every 60 minutes, for example 9:35, 10:35, 11:35, also across restarts; not on the full hour of the clock. Install.cmd starts the first run right away. StartWhenAvailable makes up a run missed while the PC was off or in standby, so the audit also runs soon after Windows starts when a slot was missed; it runs at below-normal priority, so it does not slow the start of Windows noticeably. If the PC starts shortly before a slot, the make-up run and the regular run can come a few minutes apart; that is harmless (a second toast appears only if something is wrong). Task Scheduler has no "60 minutes after the last run" setting; an earlier version combined a registration trigger and a boot trigger (5 minutes after boot) to get closer to that, which was dropped for simplicity.
- Start when available: on. A run missed while the PC was off or asleep is caught up later.
- If already running: the new run is skipped, so task runs never overlap. A manual run that overlaps with the task is handled by Audit.ps1 itself (see section 6.2).
- Time limit: 45 minutes (ExecutionTimeLimit PT45M; the Task Scheduler default is 72 hours). The audit normally finishes within a few minutes. A run that hangs, for example in a WMI or Defender query, is stopped, so it cannot block the later hourly runs: only one audit runs at a time, and a new run is skipped while one is still running.
- Priority: 8, which Task Scheduler maps to the below normal priority class (9-10 would be idle, the lowest), so foreground work runs first, but the audit still makes steady progress on a busy PC. To check the installed task, run in an elevated PowerShell: (Get-ScheduledTask -TaskName 'Security Configuration Audit').Settings.Priority

**Step 6. Register the task "Security Configuration Watchdog".**

- Runs as: the installing user, only when signed in (interactive), with least privilege (not elevated).
- Action: %ProgramFiles%\SecurityAudit\WatchDog.exe
- Trigger: an event in the Microsoft-Windows-TaskScheduler/Operational log, event ID 102 ("task completed"), for the task "\Security Configuration Audit".

Because WatchDog is started by the audit's completion event instead of its own timer, it always reads the log of an audit that has just finished. It can never read a log that a running audit is still writing. It runs unelevated in the user's session, which is all it needs: it only reads one file and shows a toast.

The Task Scheduler Operational event log must be enabled for event triggers to fire. It is enabled by default on Windows 11.

**Step 7. Start the first audit** immediately. When it completes, the watchdog runs and the operator sees a toast if anything is wrong.

Both tasks are registered from hand-built Task Scheduler XML. This gives exact control over event triggers and settings (such as the task SID and the required privileges) that the standard scheduled task cmdlets do not expose. Running the installer again replaces the copied files, both tasks (Register-ScheduledTask -Force overwrites a task of the same name) and the shortcut, and rebuilds both folder access lists, so it is safe to repeat and switches cleanly between the two modes.

### 5.3 Runtime flow

1. Every 60 minutes (counted from the installation time), the task "Security Configuration Audit" starts Audit.ps1 as LocalService (or as SYSTEM after Install.cmd -RunAuditElevated), hidden, in session 0.
2. Audit.ps1 opens SecurityAudit.log for writing, which empties it and keeps other audits out until this run ends (see section 6.2), then deletes the previous SecurityAuditErrors.log.
3. It runs all checks and writes every result to SecurityAudit.log.
4. If at least one check fails, it also writes the failures to SecurityAuditErrors.log, followed by a section with the description and security rationale of each failed check, then exits.
5. Task Scheduler records event 102 (task completed).
6. That event starts the task "Security Configuration Watchdog", which runs WatchDog.exe as the signed-in user, unelevated.
7. If SecurityAuditErrors.log does not exist, WatchDog exits silently. If it exists, WatchDog shows a toast with its contents.

### 5.4 Verifying the installation

1. Make sure notifications are on (Settings > System > Notifications).
2. Introduce drift. For example, in regedit set the DWORD value SmartScreenEnabled under HKLM\SOFTWARE\Policies\Microsoft\Edge to 0.
3. In Task Scheduler (taskschd.msc), run **Security Configuration Audit** by hand.
4. A toast should appear within about two minutes. Then fix the drift with Remediations.cmd.

### 5.5 Uninstalling

**Install.cmd -Uninstall** removes the two scheduled tasks (the watcher first, then the audit; a task that is running is stopped first) and then deletes the installation folder %ProgramFiles%\SecurityAudit, the log folder %ProgramData%\SecurityAudit (the latest audit result and the failure list go with it) and the toast shortcut "Security Configuration Alert.lnk" in the Start Menu of the user who runs the uninstall. The folders are deleted only after both tasks are gone, because a task that still exists would run files that are no longer there. The shortcut deletion removes only that one file, and only if it is an ordinary file. A WatchDog.exe that runs from that folder is stopped first, since Windows does not delete a running program. A junction or symbolic link inside a folder is removed as a link and never followed, so nothing outside the folder can be deleted; if a folder itself is a link or a file, it is left alone and reported. The three deletions run even if one fails, so as much as possible is removed. Nothing else is removed. The command needs an elevated prompt like the installation, works on any Windows version, and is safe to run again: a task or folder that does not exist is reported and is not an error. The exit code is 1 if a task, a folder or the shortcut could not be removed. It cannot be combined with -RunAuditElevated.

The only thing -Uninstall leaves is what Remediations.cmd changed in the system settings, and the state it saved for Rollback.cmd (%ProgramData%\SecurityBaseline, a different folder from the log folder). Uninstalling does **not** revert remediated settings. Use the rollback process in section 9 first if that is what you want.

## 6. Elevated and unelevated audit runs

Audit.ps1 is **read-only in the security sense**: it never changes any security configuration. By default the scheduled task runs it as LocalService, unelevated, and accepts that the checks that need administrator rights are not run: an hourly task that runs as SYSTEM is a more valuable target, and a mistake or a tampered file in it would run with full rights. Install.cmd -RunAuditElevated runs it as SYSTEM instead, which gives the complete result. An operator can also run Audit.cmd from an ordinary, unelevated prompt to see quickly which settings are not in the expected state; the complete audit still needs elevation, for the reasons below.

**How an unelevated run behaves.** Audit.ps1 checks whether its token is in the Administrators role (SYSTEM counts as elevated). Without elevation, and without -RunAuditElevated:

- Checks that need administrator rights are not run. Each one prints a yellow "[ELEVATION REQUIRED] [check] - not checked" line (also written to SecurityAudit.log when logging is on) and counts neither as passed nor as failed. They are listed by name in $script:ElevationRequiredChecks (the checks in section 6.1 that fail or return incomplete data without elevation).
- A check that is not on that list but still fails with an access-denied error is reported the same way, so a check that unexpectedly needs elevation is not shown as a false failure.
- Every other check runs normally and reports [PASS] or [FAIL].
- An interactive run writes or deletes **no log files** (see section 6.2), so WatchDog keeps showing the result of the scheduled task. Only the LocalService account, which the default scheduled task uses, writes logs without elevation.
- The summary shows how many checks were not run. The exit code is 1 if any check failed, 2 if nothing failed but some checks were not run, and 0 only when every check ran and passed (3 means the run stopped before any check because another audit was already running, see section 6.2). The LocalService task therefore normally ends with exit code 2 (Task Scheduler shows "Last Run Result" 0x2); this is expected and raises no toast.

**-RunAuditElevated.** With this switch the checks that need administrator rights must run. In an elevated run (and as SYSTEM) it changes nothing. Without elevation, each such check is reported as "[FAIL] ... not checked: this check needs administrator rights ...", and an access-denied error counts as a failure instead of [ELEVATION REQUIRED]. So if the elevated task ever ran without elevation, the gap would raise a toast instead of passing silently.

On a test PC an unelevated run skipped 55 checks (Secure Boot, TPM, BitLocker, the Security event log size, the SMBv1 and PowerShell 2.0 feature state, the remotely accessible registry paths, and the password, lockout, user-rights and other secedit-based policies) and ran the remaining checks with the same result as the elevated run.

### 6.1 Many settings can only be read by an administrator

Windows protects the state of many security features, so reading it needs administrator rights. Without elevation, these calls fail with "access denied" or return empty or incomplete data:

- **Local password, lockout and security options policy, and user-rights assignments.** Read with secedit.exe /export. Exporting the local security database (LSA policy) is an administrator operation.
- **Secure Boot.** Read with Confirm-SecureBootUEFI. Reading UEFI variables needs elevation (the SeSystemEnvironmentPrivilege privilege).
- **TPM state.** Read with Get-Tpm and the Win32_Tpm WMI class. The TPM WMI provider is restricted to administrators.
- **BitLocker status and key protectors.** Read with Get-BitLockerVolume. Encryption status and protector types are only available to administrators.
- **Defender configuration.** Read with Get-MpComputerStatus and Get-MpPreference. Unelevated callers get partial or masked values, for example for attack surface reduction rules and some protection settings.
- **Optional features (SMBv1, PowerShell 2.0).** Read with Get-WindowsOptionalFeature -Online. These DISM-based queries need elevation.
- **SMB server and client signing.** Read with Get-SmbServerConfiguration and Get-SmbClientConfiguration. Restricted to administrators.
- **Exploit mitigations, Device Guard and VBS, firewall profiles, services and event logs.** Read with Get-ProcessMitigation -System, the Win32_DeviceGuard WMI class, Get-NetFirewallProfile, the Win32_Service WMI class and Get-WinEvent. Some fields or logs are restricted or incomplete without elevation.

An elevated run counts a check that **cannot be verified** as a failure ("[FAIL] ... could not verify: ..."). An unelevated run instead reports these checks as [ELEVATION REQUIRED], so it does not show false failures; only an elevated run gives the complete result.

### 6.2 The log files belong to the scheduled task

The scheduled task writes SecurityAudit.log and SecurityAuditErrors.log in %ProgramData%\SecurityAudit, as LocalService (through its task SID, see section 5.2) or as SYSTEM. Elevated runs write them too. Each run first **replaces the previous logs** so they only ever describe the latest run. An unelevated interactive user cannot write there. A manual run that cannot replace the logs would leave old results behind, which WatchDog would then display, and its result must not replace the task's. Unelevated interactive runs therefore print their results only to the console and do not touch the log files. Audit.ps1 writes logs only when it is elevated or runs as LocalService.

**Only one audit at a time writes the logs.** A run that writes logs first opens SecurityAudit.log for writing, lets others only read it (FileShare.Read), and keeps it open until its last log line is written. There is no separate lock file. A second audit (for example an elevated Audit.cmd started while the hourly task is running, or the task starting during a manual run) cannot open the file for writing. It prints "Another security audit is already running. Wait a minute until the other audit has finished, then run Audit.cmd again.", stops before any check, deletes nothing, and exits with code 3, so it cannot mix its lines into the logs of the first run or delete its error log (the old error log is deleted only after the new log has been opened). Windows checks this when the file is opened, also when the log does not exist yet, so two runs that create it at the same moment cannot both succeed. Windows closes the file when the process ends, also after a crash, so no stale lock can remain. Unelevated interactive runs write no logs and take no lock.

**A reader can stop the audit.** A program that opens SecurityAudit.log for reading without allowing writers (FileShare.Read, the default of .NET's File.OpenRead) stops the audit in the same way as a second audit does: the audit exits with code 3 before any check and without a toast, because the two cases cannot be told apart. Everyone may read the logs, so such a program could keep the audit from running. This is accepted for simplicity: an earlier version used a separate lock file that only SYSTEM, Administrators and the audit task could open, which avoided this, at the cost of creating that file with its own access list during installation. WatchDog opens the log in a way that allows writers, so it is not affected.

After taking the lock, the run deletes the previous SecurityAuditErrors.log and opens SecurityAudit.log for writing, which also empties it. Everyone, including unelevated processes, can read both files while the audit runs. If a program holds one of them open in a way that blocks writing, the audit does not stop: it reports "[FAIL] Audit log — ..." as a failure, which raises a toast. If SecurityAudit.log is blocked, that run has no full log, and the failure is written to SecurityAuditErrors.log. If the old SecurityAuditErrors.log cannot be deleted, it cannot be rewritten either, so WatchDog shows the failures of the earlier run. Programs that only view a log (Notepad, Get-Content and most editors) allow writing and are not affected. WatchDog reads SecurityAuditErrors.log only after the audit has finished.

### 6.3 Consistent view of the machine

Running as SYSTEM or as an elevated administrator gives every run the same machine-wide view: HKLM policy keys, all user profiles and all services. The results then do not depend on who happened to start the audit. LocalService sees the HKLM policy keys and services, but not the user profiles: a browser installed only in a user's AppData\Local is not found by the LocalService task, so its browser checks are not run. Browsers installed in Program Files are found in both modes.

## 7. Audit engine design (Audit.ps1)

### 7.1 Check model

Every check is one call to the Test-Setting function, with three arguments: the check name, the expected state as text, and a script block that does the check.

- If the script block returns $true, the check passes. A green "[PASS]" line is written.
- If it returns $false, $null or a text, the check fails. A red "[FAIL] ... expected: ...; observed: ..." line is written. If the script block returned text, that text is used as the "observed" detail.
- If the script block fails with an error, the check also fails, with "could not verify: [error]". A setting that cannot be verified is treated as non-compliant (fail closed).
- If the check is **audit-only**, its failure message ends with "Not fixed by Remediations.ps1:" followed by the reason and what to do instead. Audit-only checks are those listed in $script:NotRemediatedReasons in Audit.ps1, for example Secure Boot, TPM, BitLocker and Tamper Protection. The same items are marked audit-only in SecurityBaselineSettings.html, and the two lists must stay aligned.

Helper functions cover common patterns: Test-RegDword, Test-RegString, Test-RegMultiString, Test-CisServiceDisabled, Test-CisUserRight and Test-BrowserExtensionPolicy. The secedit exports are cached for the run (Get-CachedLocalSecurityPolicy and Get-CachedUserRights), so each policy area is exported only once. Simple CIS settings that are a single registry DWORD are kept in one table, $cisAdditionalRegistrySettings, which exists with identical content in Audit.ps1 (one check per entry) and Remediations.ps1 (one setting per entry).

The checks themselves are documented in SecurityBaselineSettings.html.

**Defender extended cloud check.** On Windows 10 22H2 (seen with Defender platform 4.18.26100.4), Get-MpPreference reports CloudExtendedTimeout as 0 even after Set-MpPreference -CloudExtendedTimeout 50 has stored 50 (MpBafsExtendedTimeout under HKLM\SOFTWARE\Microsoft\Windows Defender\MpEngine); Windows 11 with the same platform reports 50. Remediations.ps1 then reported "Verification failed" and changed the setting again on every run. Both scripts therefore read the value through Get-DefenderCloudExtendedTimeout (identical in both): when the cmdlet reports less than 50, the stored value decides, the policy value under HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\MpEngine if one exists (it overrides the local value), otherwise the local value. Both keys are readable without elevation. Analyze uses the same function.

**Per-user policies (CIS section 19).** These policies live in each user's own registry hive, HKEY_USERS\<SID>, not in HKEY_LOCAL_MACHINE. The audit checks them for every loaded user profile of a local or domain account (a SID that starts with S-1-5-21). An elevated run reads all loaded hives. A run without elevation can only read its own account's hive, so for the default LocalService task, which is not a user account, these checks are reported as needing elevation. When an elevated run finds no loaded profile, it prints one [SKIP] line. Users who are not signed in are not checked, and a user can change their own policy values.

### 7.2 Outputs

- **Console** (interactive runs only): a header with the computer name, Windows version and build, the time, and when the PowerShell process started (with the seconds until the log was opened, which shows a slow start, for example right after the PC woke from standby); then colored PASS and FAIL lines, the totals, and the verdict "Computer is secure" or "Computer is insecure". The totals line counts the checks that failed (the setting does not meet the expectation) and the checks that are unverified (the setting could not be read, or a check that must run needed elevation) separately: "Checks run: N; failed: X; unverified: Y; not run because elevation is required: Z". Both count against the result and give exit code 1. When the verdict is "insecure", the paths of SecurityAudit.log and SecurityAuditErrors.log are printed last, or a note that no log was written, because only an elevated audit or the scheduled task writes logs. After the ASR rules check, an [INFO] block reports event 1122 from the Microsoft-Windows-Windows Defender/Operational log (an ASR rule in Audit mode matched): the newest ten events with rule, process, path, user and command lines, or, when there are none, a hint to consider switching the PsExec and WMI rule from Audit to Block, with the Add-MpPreference command to do it. It is also written to SecurityAudit.log, is read-only and never counts as a check or a failure.
- **SecurityAudit.log** in %ProgramData%\SecurityAudit: the full log of every check from the latest run, with time stamps.
- **SecurityAuditErrors.log** in %ProgramData%\SecurityAudit: the failure lines from the latest run, and a "Details of the failed checks" section after them (see section 7.5). The details are kept after all failure lines because WatchDog's toast shows the start of the file, so the toast still lists the failures, and its "Open log" button opens the whole file. It is created only if at least one check fails. Whether it exists is the signal WatchDog uses.
- **Exit code:** 0 means all checks passed. 1 means at least one check failed or could not be verified. 2 means nothing failed but some checks were not run because elevation is required. 3 means the run stopped before any check, because another audit is already running and writing the logs, or a program has SecurityAudit.log open without allowing writers (see section 6.2). A log file that cannot be written does not stop the run; it is reported as a failure.

Both logs describe the latest audit only. At the start of a run, the previous SecurityAudit.log is copied to SecurityAudit.previous.log before the log is emptied, so the log of the run before stays available for troubleshooting (for example a run that the task's time limit stopped). The copy is made only while this run holds the log, so a second audit that is refused (exit code 3) changes neither file; if the copy fails (for example because a program has the previous log open), the run continues and notes it as an [INFO] line. The summary line ends with the duration of the run, counted from the process start ("; duration: 70 seconds").

### 7.3 Browser handling

Edge and Chrome are handled independently. A browser counts as installed if its program file exists in Program Files, in Program Files (x86), or in AppData\Local of any user profile listed in the registry (HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList). If a browser is not installed, its checks are skipped, and Remediations.ps1 does not set its policy keys.

Each browser has its own extension allow-list, because the same extension can have different IDs in the Edge Add-ons store and the Chrome Web Store. The lists must be identical in Audit.ps1 and Remediations.ps1. The audit passes when the browser blocks all extensions by default (ExtensionInstallBlocklist contains *) and no enabled extension outside the approved list is installed in any browser profile of any local user. Installed but disabled extensions are allowed; the on/off state comes from the profile's Secure Preferences and Preferences files (a non-zero disable_reasons, or the older state = 0, means disabled), and an extension without an entry counts as enabled (fail closed). An installed extension is not reported when (a) its folder has no manifest.json (a leftover the browser cannot load), (b) the browser saved it as disabled, or (c) the machine policy blocks it: ExtensionInstallBlocklist contains *, the machine ExtensionInstallAllowlist key exists (so per-user policy cannot widen it), no ExtensionSettings policy overrides these lists, and its ID is neither on the registry allow-list nor in ExtensionInstallForcelist. The browser checks this policy before loading extensions, so such an extension cannot run even while a user's saved state still says enabled (until that user starts the browser again, which then disables it). As a result the audit passes right after Remediations.ps1 has set the policy. A failure names each enabled unapproved extension (from its manifest.json, including translated names), with its ID and the Windows user and browser profile, comma-separated. Approved extensions do not have to be installed, and the registry allow-list is not compared with the approved list, so adding an ID does not make the audit fail before Remediations.ps1 runs again.

Chrome has seven more policy checks, taken from the CIS Google Chrome Group Policy Benchmark v1.1.1. That benchmark is written for managed PCs, so only the recommendations that fix a clear security problem on a stand-alone PC are used:

| Check | Registry value | Expected | CIS |
|---|---|---|---|
| Chrome Safe Browsing Protection Level | SafeBrowsingProtectionLevel | 1 (standard) or 2 (enhanced) | 2.15.2 |
| Chrome Safe Browsing Warnings Cannot Be Bypassed | DisableSafeBrowsingProceedAnyway | 1 | 2.15.3 |
| Chrome Download Restrictions | DownloadRestrictions | 4 (block malicious downloads), or the stricter 1, 2 or 3 | 2.42 |
| Chrome Component Updates | ComponentUpdatesEnabled | 1 | 2.37 |
| Chrome Automatic Updates | Update{8A69D345-D564-463C-AFF1-A69D9E530F96} under HKLM\SOFTWARE\Policies\Google\Update | 1 (always allow updates) or 3 (automatic updates only) | 4.2 |
| Chrome Remote Debugging Disabled | RemoteDebuggingAllowed | 0 | 2.69 |
| Chrome Application-Bound Encryption | ApplicationBoundEncryptionEnabled | 1 | 2.88 |

All values are DWORDs under HKLM\SOFTWARE\Policies\Google\Chrome unless the table says otherwise. The settings live in one table, $chromePolicySettings, which must be identical in Audit.ps1 and Remediations.ps1. Value is what Remediations.ps1 writes; AlsoAccepted lists values that are just as safe (enhanced Safe Browsing, stricter download restrictions, automatic-only updates). The audit passes on any of them, and Remediations.ps1 leaves them unchanged (the Accept parameter of Set-IdempotentDword). Every value the remediation writes is recorded for the rollback like any other registry value.

The PDF names no data type or value meaning, so the values follow Google's own policy definitions (chromeenterprise.google/policies and, for the update policy, the Google Update policy list), which are more authoritative than the benchmark for Chrome's own settings. They disagree in one case: CIS 2.11.1 ("Ensure 'Enable leak detection for entered credentials' is set to 'Enabled'") prints the registry value PasswordLeakDetectionEnabled = 0, but in Google's definition 0 (false) turns leak detection off and 1 (true) turns it on. Following the CIS value literally would turn off the protection the recommendation asks for. The recommendation is not adopted (Chrome checks for leaked credentials by default unless the user turns it off, and the rest of the baseline does not rely on Chrome's password manager); if it is adopted later, the value must be 1.

### 7.4 Parameters

- **-RestrictTo [list]**: audits only the listed systems, separated by commas: **OS** (Windows itself), **Edge** (the Microsoft Edge policies) and **Chrome** (the Google Chrome policies). Not case sensitive; -RestrictTo Edge,OS and RestrictTo=Edge,OS both work (Audit.cmd passes its arguments on). Unknown or misspelled names are ignored with a warning and the supported ones still run; if none is left, the audit stops with exit code 1. Without it everything is audited. A restricted run writes no log files, so the result of the scheduled full audit that WatchDog shows is never replaced by a partial one, and its final line says which systems were audited instead of "Computer is secure". In the script, the OS checks sit in two blocks guarded by Test-SystemSelected 'OS' (before and after the browser checks), and the browser loop skips a browser that is not selected.
- **-ApprovedAdministratorsFile [path]**: a text file of approved local administrator accounts, one per line. Lines starting with # are comments. Without it, the administrator membership check is reported as not configured.
- **-MaximumSignatureAgeDays [number]**: the maximum allowed age of Defender signatures, in days. The default is 3.
- **-RunAuditElevated**: the checks that need administrator rights must run; without elevation they are failures instead of [ELEVATION REQUIRED] (see section 6). Install.cmd -RunAuditElevated registers the scheduled task as SYSTEM with this switch.

### 7.5 Failure details

After each failed check, Audit.ps1 always prints what the setting does (Description), why it matters for security (Why it matters) and the source. There is no switch to turn this on or off. All text comes from AuditCheckDetails.json (see section 2.1): checks named "CIS <id> ..." use its copy of the CIS benchmark text, and the other checks use its hand-written entries. The file is only read. If it is missing or unreadable, a warning is shown and the audit runs without the details. The details are written to the console, to SecurityAudit.log right under each failure line, and to SecurityAuditErrors.log in a section after all failure lines (see section 7.2). The exit code, the result and the failure lines themselves do not depend on the details. Because the scheduled audit task runs the same script, the logs of the hourly audit contain the details too.

Earlier versions turned the details on with a -VerboseErrorDetails switch, and scheduled tasks installed by those versions pass it. Audit.ps1 no longer accepts it, so such a task fails before it runs any check and leaves the previous logs in place. Run Install.cmd again after deploying this version; it re-registers the task without the switch.

## 8. Remediation (Remediations.ps1)

### 8.1 Principles

- **Stand-alone PCs only.** Before anything else, including creating the rollback folder, Remediations.ps1 checks whether an organization manages the PC (the Get-OrganizationManagementFinding function). Signs of management are: an Active Directory domain join (which domain Group Policy needs), a Microsoft Entra or on-premises device join or a registered work or school account (from dsregcmd /status and the CloudDomainJoin registry key), an MDM enrollment with an MDM server (such as Intune), or the Configuration Manager client or Intune Management Extension service. If any sign is found, or the domain, Entra ID or MDM state cannot be read, the script stops with the list of findings and makes no changes. The check only reads state. Audit.ps1 and Rollback.cmd do not run this check, so a PC that was joined or enrolled later can still be audited and rolled back. Third-party remote management tools that do not use these Windows mechanisms are not detected.
- **Idempotent.** Every step reads the current state first and changes only what is not compliant. Compliant and unrelated settings are left alone. Where the audit accepts more than one value (for example LDAP client signing 1 or 2, or an SMB idle timeout of 1 to 15 minutes), an existing accepted value is kept, so a stricter setting is never weakened; the setter functions take the accepted values through their -Accept and -AcceptedValues parameters. Running it again is safe, and a second run on a compliant machine makes no changes.
- **Verify after writing.** Setter functions such as Set-IdempotentDword read the value back and fail if it does not match.
- **Per-user policies only for loaded profiles.** The CIS section 19 policies are set in HKEY_USERS\<SID> for every user profile that is loaded (signed in) when the script runs, and the old values are recorded for rollback like any other registry value. Another user gets them when Remediations.ps1 runs while that user is signed in. Rollback restores the values only while the same profile is loaded. A sign-out is needed for them to take full effect.
- **Record before changing.** The original state of every setting the script checks is saved to the rollback snapshot the first time the setting is seen, before any change is applied, and it is saved even when the setting needs no change (see section 8.2). For each setting the snapshot also notes whether it was already in its expected state or was corrected.
- **A failed step does not stop the run.** The setter functions (Set-IdempotentDword, Set-IdempotentString, Set-IdempotentMultiString, Remove-IdempotentRegistryValue and Set-BrowserExtensionPolicyList) report a failure with Write-Error and return instead of throwing, and the other steps are wrapped in try/catch. One failure is therefore reported without stopping the remaining remediations.
- **One run at a time.** Remediations.ps1 and rollback.ps1 take an exclusive lock, the file %ProgramData%\SecurityBaseline\SecurityBaseline.lock, opened with no sharing and with DeleteOnClose, right after the snapshot folder has been checked and protected. A second Remediations.ps1 or rollback.ps1 that starts while the first runs stops at once, before changing anything ("another Remediations.ps1 or rollback.ps1 is already running"); without this, both would keep their own copy of the snapshot, the later save would overwrite the other's records, and a run that started after another had changed a setting would record that new value as the original. The file has a neutral name because it protects both scripts and any pair of runs (two remediations, two rollbacks, or one of each), and the name is the same for every run on purpose, because the runs must open the same file to notice each other; it cannot collide with other files in the folder (the other names are Remediations.rollback.clixml, rollback.ps1, the two saved .inf exports and temporary files with a random GUID in the name). Windows deletes the file and frees the lock when the run ends, also after a crash or when the process is killed, so no stale lock can stay behind; the rest of the script runs in a try/finally block that also releases it in a PowerShell window that stays open. The folder is writable only by SYSTEM and Administrators, so no other account can hold or plant the lock file. Remediations.cmd Analyze and the help only read and do not take the lock.
- **Restart awareness.** Some steps need a restart (for example Memory Integrity and other virtualization-based security, LSA protection, exploit mitigations, NetBIOS and the TLS/SSL protocol versions). Others need a sign-out (for example user rights and AutoRun). Each step records its reason only **if it changed something in this run**, and a summary is printed at the end. When a restart is required, the summary adds a note to make sure the Microsoft account user name, password and PIN are known and working before restarting (and, for passwordless sign-in, that the Microsoft Authenticator app or hardware security key is at hand and works), because changes such as Memory Integrity, Credential Guard and LSA protection can change how sign-in works afterwards.
- **No irreversible changes.** For example, LSA protection is set to RunAsPPL = 2 (no UEFI lock), because a setting locked in UEFI cannot be undone by a registry rollback. On Windows builds that only support the UEFI-locked form, the step is skipped with a warning. For the same reason, Memory Integrity (CIS 18.9.5.3) and Credential Guard (CIS 18.9.5.5) are set to 2 ("Enabled without lock") instead of the CIS value 1 ("Enabled with UEFI lock"); the audit accepts both. The Recall policy (CIS 18.10.73.1) is set only when the Recall optional feature is not enabled, because turning Recall off deletes its saved snapshots, which rollback cannot restore. A UEFI lock that an earlier version of Remediations.ps1 set stays in the firmware; rollback.ps1 cannot remove it.
- **No risky driver changes.** Memory Integrity blocks incompatible kernel drivers, and a blocked driver that Windows needs to start can stop it from booting. Remediations.ps1 therefore sets the Memory Integrity policy only when Memory Integrity is already running. Otherwise it warns, and the operator turns it on in Windows Security, which checks the drivers first.
- **Audit-only items are left alone.** Items that cannot or should not be scripted are reported by the audit with guidance instead. Examples are firmware settings, BitLocker, Tamper Protection, and disabling the built-in Administrator account (which could lock you out). CIS 18.9.29.1 (Block User from Showing Account Details on Sign-in) is an intended exception to CIS for usability: with it on, the sign-in screen hides the account name and e-mail address and the Windows setting "Show account details such as my email address on the sign-in screen" is turned off. The audit prints an [INFO] message about it, it is never a failure, Remediations.ps1 does not set it, and a value of 1 that is already there is left as it is. CIS 18.10.80.1 (Enhanced Sign-in Security) goes one step further: the audit only prints an [INFO] message about it and never counts it as a failure, because it is recommended but older laptops whose camera or fingerprint reader does not support it lose Windows Hello when it is on (the sensor is blocked and the saved enrollments are deleted), and missing hardware support cannot be fixed. Remediations.ps1 does not set it and prints a note about that.

### 8.2 Rollback state recording

The original state is collected in memory in $script:UndoState (format **version 2**) and saved to disk after each recorded change and once more at the end of the run. It holds:

- **Created and ComputerName:** when the snapshot was created and the name of the computer it was created on. A snapshot from an older version of the script gets the name of the computer it is on when it is first loaded.
- **SettingOutcomes:** for every setting the script checked, when it was first seen (FirstSeen), what happened then (FirstOutcome: AlreadyInExpectedState, Corrected, or NotCorrected when the correction was skipped or failed) and when the script last corrected it (LastCorrected, empty if never). FirstOutcome is never changed by later runs, so a setting that was already right at the start stays marked as such even if the script has had to correct it since. A snapshot from an older version of the script recorded only settings it had changed, so a setting that such a snapshot already had a record for is marked Corrected, with the creation date of the snapshot as FirstSeen. The script prints the totals when it finishes.
- **Changes:** a readable list of every recorded change, for example "Registry HKLM:\...\Name: restore DWord value 0" or "Service X: restore startup mode Auto and state Running".
- **RegistryKeys:** for every key on the path of a changed value, whether it existed before. Used to delete keys that remediation created.
- **RegistryValues:** for each value the script checks, whether or not it changes it, whether it existed, its value type, and its original data (with environment variables not expanded).
- **RegistryKeysWithCompleteValueSet:** keys whose entire set of values was saved, for example the browser extension allow and block lists, so rollback can restore the exact list.
- **Services:** the original startup mode and running state of every installed service on the baseline list (and of the services stopped together with them).
- **OptionalFeatures:** the original state of the PowerShell 2.0 features that exist on the PC, enabled or not.
- **AuditPolicy, FirewallProfiles and EventLogMaximumSizes:** the original advanced audit policy subcategories, firewall profile defaults, and the original sizes of the Application, Security, Setup and System event logs (by log name, only for logs whose size was raised; older snapshots store the Security log size in SecurityLogMaximumSize, which rollback still restores). Each log size has two parts: the size the log uses (raised to the CIS minimum with wevtutil and restored with wevtutil) and the CIS 18.10.26 policy value MaxSize (a registry value, restored by the registry step, which runs first). Because the policy takes precedence over the size in the log properties, MaxSize is set to the larger of the CIS minimum and the size the log uses, so a larger size is never lowered.
- **SecurityPolicyFile and UserRightsPolicyFile:** paths to secedit exports of the local security policy and user-rights assignments, taken just before the script changes them. The security policy export is taken after the registry remediation, so its security-option registry values are already hardened; rollback therefore uses only the account-policy settings from it (see section 9.2).
- **UserRightsManagedRights:** the names of the user rights that remediation sets. The export leaves out rights that have no accounts, so rollback needs this list to empty rights that had no accounts before.
- **GuestAccount, SMB signing, Defender settings and ExploitMitigations:** the original values of the built-in Guest account, SMB signing, Defender Controlled Folder Access, Network Protection, PUA Protection and attack surface reduction rules, and system exploit mitigations. A Defender setting is recorded only after Defender has returned the current value. If the change itself fails, the entry that announced the change is removed again, but the recorded original stays.

Saving is **atomic**. The Save-UndoState function writes to a temporary file with a unique name and then moves it over the snapshot. An interruption therefore never leaves a half-written snapshot. Each save also regenerates rollback.ps1.

**Settings that need no change are recorded too.** Every setting the script checks is recorded the first time it is seen, whether or not it has to be changed, so that a rollback always returns to the real starting point, even for a setting that was already right at first and was changed by hand and corrected later. Only a registry key that exists is recorded, because rollback deletes keys that are recorded as new: a key is recorded as new only when the script creates it. The four system exploit mitigations are the exception: only a mitigation that is explicitly off is recorded, because the state "not set" cannot be restored for a single mitigation. A snapshot with about 330 settings takes roughly 0.4 MB. A run on a PC where nothing needs a change therefore still creates a snapshot (with an empty Changes list), and Rollback.cmd then has nothing to change.

**The snapshot builds up across runs.** If a snapshot already exists when Remediations.ps1 starts, it is loaded and extended, not replaced. The first recorded original value of a setting is always kept. So after several remediation runs, a rollback still returns the machine to its state **before the first remediation**.

When Remediations.ps1 starts, it also checks the snapshot:

- If both the current snapshot (Remediations.rollback.clixml) and the old name (Remediations.undo.clixml) exist, it stops instead of risking overwriting rollback state.
- A snapshot with the old name is renamed to the current name.
- A **version 1** snapshot, which may contain unchanged settings, blocks remediation. The script generates rollback.ps1 for it and asks the operator to roll back first.
- If no snapshot exists, any old rollback.ps1 is deleted so it cannot be run by mistake.

### 8.3 Change report

When a run changes settings, Remediations.ps1 writes a Markdown report and prints its full path at the end ("Report of the applied changes: ..."). The file is %ProgramData%\SecurityBaseline\Remediations-report-yyyyMMdd-HHmmss.md, one per run, in the administrators-only snapshot folder. A run that changes nothing writes no report and says so instead ("No change report was written, because this run changed no settings").

The report has one table row per setting the run changed: the setting (in the short form of Remediations.cmd Analyze, section 9.3, for example a registry value joined to its key path), the old value, the new value, and why the baseline wants it.

- **Which settings:** every setting for which Set-SettingOutcome recorded "Corrected" during this run. For settings with several values (local security policy, user rights, firewall profiles, ASR rules, a registry key with a complete list of values), only the values that differ are listed. A change whose values the report cannot read (for example a registry key that was only created) is listed as "not recorded -> changed".
- **Old value:** the value just before this run. Before changing anything, the run reads the current value of every setting an earlier run recorded (the same reading as Analyze, so a rerun takes some seconds longer). A setting recorded for the first time in this run takes its old value from the snapshot, which recorded it just before the change.
- **New value:** read after the run, like the "now" column of Analyze.
- **Why:** taken from AuditCheckDetails.json next to the script: the CIS rationale (with the CIS number) when the setting belongs to a CIS recommendation, found by the CIS number in the recorded description or by the setting's name in the recommendation title (services, audit policy, event log sizes, firewall, user rights, password and lockout policy, Guest account, SMB signing); otherwise the rationale of the matching audit check (Defender, SmartScreen, LLMNR, exploit protection and others); for the browser extension list, password export and browsing data lifetime, the reason from SecurityBaselineSettings.html. When none is found, the row points to SecurityBaselineSettings.html.

Values are shortened to 60 characters and stripped of control characters, as in Analyze. The report only reads settings; it changes nothing.

## 9. Rollback

### 9.1 How rollback.ps1 is generated

rollback.ps1 is **generated code**, not a file in source control. The Write-GeneratedRollbackScript function in Remediations.ps1:

1. reads Remediations.ps1 itself with the PowerShell parser,
2. copies out the complete text of the Invoke-Rollback function,
3. writes rollback.ps1 in %ProgramData%\SecurityBaseline, next to the snapshot, not next to Remediations.ps1, so the script folder can be read-only (for example a synced or write-protected folder). The file contains a comment listing every **recorded rollback entry** (the Changes list), so the operator can read what will be restored before running it. Then comes the copied Invoke-Rollback function, and finally a call to it.

So the rollback logic is maintained in one place (inside Remediations.ps1), and the generated script is **self-contained**. It does not need Remediations.ps1 to be present, and it always matches the snapshot format of the version that wrote it.

rollback.ps1 is generated whenever a snapshot is saved. A run that changed something lists the changes in its header; a run on a machine that was already compliant creates a snapshot with no listed changes, which only records the original state.

### 9.2 Running a rollback

From an elevated prompt, run Rollback.cmd (it runs %ProgramData%\SecurityBaseline\rollback.ps1), or run that rollback.ps1 directly in an elevated PowerShell window. The Invoke-Rollback function first takes the same run lock as Remediations.ps1 (section 8.1, "One run at a time"), so a rollback cannot overlap a remediation or another rollback; it then:

1. Loads %ProgramData%\SecurityBaseline\Remediations.rollback.clixml. Snapshot versions 1 and 2 are supported.
2. Restores each kind of setting as a separate step, so one failure does not stop the others:
    - **Registry.** Restores the original values (type and data), deletes values that did not exist before, resets keys whose complete value set was saved to exactly their original values, and deletes keys that remediation created (deepest first). A value that already equals the original is skipped. Each change is reported as "Rolled back X from A to B".
    - **Guest account:** returned to its original state: enabled again if it was enabled, disabled again if it was disabled and has been enabled since.
    - **Local security policy and user rights:** restored with secedit /configure from temporary .inf files built from the saved exports. For the security policy, only the password, lockout and account-policy settings that remediation changes are applied; the registry values, account names and Administrator/Guest account states in the export are left out, because applying them would undo the registry and Guest account rollback. For user rights, the saved assignments are applied, and every managed right that is missing from the export (it had no accounts) is set to empty.
    - **Services:** original startup type of every saved service restored first, then the services that were stopped (a service cannot start while a service it depends on is disabled), then the services that were running are started. Services are saved in no particular order, so the three passes make the order irrelevant. Remediations.ps1 stops a service together with the running services that depend on it (Windows refuses otherwise, for example XblGameSave depends on XblAuthManager) and saves their state first, so this step starts them again. It does this only when every running dependent is itself one of the services the baseline disables; if another running service depends on it (for example the Workstation service, which carries network drives and shares, depends on the Computer Browser service), the service is skipped, left exactly as it was, with a message saying which services it would also stop, and the audit keeps reporting it.
    - **Optional features:** returned to their original state, without restarting: enabled again if they were enabled, disabled again if they were disabled and have been enabled since.
    - **Advanced audit policy** (with auditpol /set), **firewall profiles**, and the **Security event log size** (with wevtutil).
    - **SMB signing**, **Defender** Controlled Folder Access, Network Protection, PUA Protection and attack surface reduction rules, and **system exploit mitigations**.
3. **If everything succeeds**, it deletes the snapshot, the saved .inf policy exports, and rollback.ps1 itself, then reminds the operator that a restart may be needed.
4. **If any step fails**, it keeps everything and stops with a list of the failed steps. The operator can fix the cause and run the same rollback.ps1 again. Steps that already succeeded are harmless to repeat.

### 9.3 Analyzing the snapshot

Remediations.cmd Analyze (elevated, because the snapshot folder is administrators-only) prints what Remediations.ps1 changed, without changing anything. It reads the snapshot and the current state of the PC and prints one short line per setting, "setting original -> now", grouped by kind: Registry, Services, Local security policy, User rights, Windows features, Accounts, Network, Firewall, Audit policy, Event logs, Defender and Exploit mitigations. Lines are kept short on purpose:

- **Registry values** show the value name joined to the key path and leave out the data type and whether the value existed; an absent value shows as (none). Example: HKLM:\SOFTWARE\Policies\Microsoft\Edge\SmartScreenEnabled 0 -> 1.
- **Services** show the display name and the start mode, with the running state added when it changed too. Example: Xbox Live Auth Manager Manual (Running) -> Disabled (Stopped).
- The other settings use short names, for example "Security event log size 64 MB -> 192 MB", "Guest account Enabled -> Disabled" or "Defender cloud block level Default -> High". User rights show the account names instead of SIDs.

"Now" is read live, so it also shows settings that were changed again after the run. Every recorded setting is listed; those that differ from their original value are printed in yellow (the highlight color Audit.ps1 uses), and a last line gives the counts. A value that cannot be read is shown as "unknown" and highlighted. Values are cut after 60 characters and stripped of control characters before printing. Analyze exports the current local security policy to a temporary file in the snapshot folder to compare it, and deletes the file again. Without a snapshot it only says so.
These are not rolled back:

- **Audit-only items**, because remediation never changed them.
- **The scheduled tasks and the toast shortcut.** These are installation items, not remediations. See section 5.5.

After a rollback, the scheduled audit will (correctly) report the restored settings as drift. Uninstall the tasks too if you are leaving the baseline for good.

## 10. Files and folders written on the system

### 10.1 Audit log folder: %ProgramData%\SecurityAudit

- **The folder itself.** Created by InstallTasks.ps1 and Audit.ps1. Stays in place. InstallTasks.ps1 limits writing to SYSTEM, Administrators and, in the default mode, the audit task's SID (see section 5.2, step 3); an elevated run of Audit.ps1 that finds no folder creates it together with a protective access list (SYSTEM and Administrators full control, Users read), so the permissions inherited from ProgramData, which let every user create files, never apply to it. An existing folder is used only if it is a real folder owned by SYSTEM or Administrators (see section 11, "Folders in ProgramData"); otherwise Audit.ps1 writes no logs and reports this as a failure, and Install.cmd stops.
- **SecurityAudit.log.** Written by Audit.ps1. The full log of the latest run. Replaced on every run.
- **SecurityAuditErrors.log.** Written by Audit.ps1. The failure lines of the latest run, followed by the details of the failed checks (see section 7.5), read by WatchDog. Deleted on every run and created again only if a check fails.
- **SecurityAudit.previous.log.** Written by Audit.ps1. The SecurityAudit.log of the run before, replaced on every run. For troubleshooting only; nothing reads it.

### 10.2 Rollback state folder: %ProgramData%\SecurityBaseline

- **The folder itself.** Created by Remediations.ps1. Stays in place. Every run of Remediations.ps1 gives it its own access list without inheritance, so only SYSTEM and Administrators can read or change it, and stops without changing anything if a file in it is owned by another account. Without this, ProgramData would let a standard user plant or edit a file (for example rollback.ps1 or a saved security policy) that an administrator later runs or applies elevated. This protects the tool's own state and is not a baseline setting, so rollback does not undo it.
- **rollback.ps1.** Written by Remediations.ps1. The generated, self-contained rollback script, run by Rollback.cmd. Kept until a successful rollback. Older versions wrote it next to Remediations.ps1; Remediations.ps1 deletes such an outdated copy when that folder allows it, and warns otherwise.
- **Remediations.rollback.clixml.** Written by Remediations.ps1. The rollback snapshot (version 2). Kept until a successful rollback.
- **Remediations.security-policy.inf.** Written by Remediations.ps1, only if the security policy is changed. A secedit export of the original security policy. Kept until a successful rollback.
- **Remediations.user-rights.inf.** Written by Remediations.ps1, only if user rights are changed. A secedit export of the original user rights. Kept until a successful rollback.
- **Files ending in .sdb.** Working databases that secedit creates during remediation and rollback. Left in place.
- **Temporary secedit files** (CisUserRights-*.inf, SecurityPolicy-*.inf and their .sdb databases). Written by Remediations.ps1 while it reads and applies the security policy, and deleted afterwards. They are kept here, not in the temp folder: the temp folder of an elevated administrator is the user's own, where a non-elevated process could change a policy file between writing it and applying it.
- **Remediations.undo.clixml.** The snapshot name used by older versions. Renamed automatically.

### 10.3 Other locations

- **%ProgramFiles%\SecurityAudit** with Audit.ps1, AuditCheckDetails.json and WatchDog.exe. Written by InstallTasks.ps1, which also sets its permissions (see section 5.2, step 2). The scheduled tasks run these copies. Replaced by every run of Install.cmd. Stays in place.
- **WatchDog.log and WatchDog.old.log** in %LOCALAPPDATA%\SecurityAudit of the signed-in user. Written by WatchDog.exe, one line per run (see section 2). Not removed by Install.cmd -Uninstall, which runs as an administrator and cannot know every user's folder; delete it by hand if wanted.
- **Security Configuration Alert.lnk** in %APPDATA%\Microsoft\Windows\Start Menu\Programs. Written by InstallTasks.ps1. Registers WatchDog's identity for toasts. Stays in place.
- **The scheduled tasks** "\Security Configuration Audit" and "\Security Configuration Watchdog". Created by InstallTasks.ps1. Stay in place.
- **Registry, services, policies, Defender, firewall and other settings.** Changed by Remediations.ps1. These are the baseline settings themselves (see SecurityBaselineSettings.html). They stay until changed again or rolled back.

Audit.ps1 also writes temporary secedit export files and deletes them after reading them. An elevated run writes them to the audit log folder, which only SYSTEM and Administrators can write, so a non-elevated process cannot replace an export before it is read.

## 11. Security considerations

- **Least privilege for the hourly audit.** By default the audit task runs as LocalService, not elevated, with its own task SID and only SeChangeNotifyPrivilege (see section 5.2, step 5). Only that task SID, not every LocalService process, can read the install folder through its own entry and write the log folder. The logs the task creates are owned by LocalService; an OWNER RIGHTS entry on the log folder takes away the owner's right to change their permissions, so no other LocalService process can take them over (section 5.2, step 3). The price is that the checks that need administrator rights are not run hourly; run Audit.cmd elevated now and then, or install with -RunAuditElevated.
- **Protected install folder.** The tasks run their files from %ProgramFiles%\SecurityAudit, which only SYSTEM and Administrators can change, never from the folder Install.cmd was started from. Anyone who could change Audit.ps1 could run code as the task's account (SYSTEM with -RunAuditElevated) at the next hourly run. The folder you deploy from, for example the publish folder in your profile or a synced folder such as OneDrive, can still be changed by its owner, but such a change only takes effect when an administrator runs Install.cmd again. Check what you install before running Install.cmd.
- **Detection only, by design.** The scheduled task never fixes settings automatically, so an attacker or a buggy script cannot use it to change configuration. Fixes always need an operator at an elevated prompt.
- **Folders in ProgramData.** Every user can create folders and files directly under %ProgramData%, so a folder name the suite uses (SecurityAudit, SecurityBaseline) could be created by someone else before the first run, as a folder they keep access to, or as a junction or symbolic link that redirects the access list and the files to another place. Audit.ps1, InstallTasks.ps1 and Remediations.ps1 therefore create a missing folder together with its access list in one step, and use an existing one only if it is a real folder owned by SYSTEM or Administrators. Otherwise they stop (Audit.ps1: no logs and a reported failure) and ask for the folder to be checked and deleted.
- **Elevated sessions do not trust what the signed-in user can change.** A non-elevated process running as the administrator's own account can write to that account's Documents folder, temp folder and environment variables. The scripts therefore (1) load PowerShell modules only from Windows and Program Files, not from the user's Documents folder; (2) start secedit, auditpol, wevtutil and powershell.exe by full path, never through the current folder or PATH; (3) take the Windows, Program Files and ProgramData folders from Windows instead of from environment variables; and (4) keep the policy files that Remediations.ps1 applies in the administrators-only state folder instead of the temp folder. The .cmd wrappers still expand %SystemRoot% to start fltmc.exe and powershell.exe, which cmd.exe can only read from the environment. Rollback.cmd does not use %ProgramData%: a non-elevated process can set a user environment variable of that name, which an elevated Rollback.cmd would then use to find the script it runs, so PowerShell takes the folder from Windows instead.
- **What the scripts cannot protect.** Remediations.cmd, Rollback.cmd, Install.cmd and Audit.cmd run whatever is in the folder they are started from. If that folder can be changed by a non-elevated process (the publish folder in the user profile, a synced folder), that process can change a script and wait for an administrator to run it elevated. Run them from a folder only administrators can change, or check the files first. For the same reason, a daily-use account that is itself an administrator (UAC consent prompt) is weaker than a standard account with a separate administrator account: Microsoft does not treat the consent prompt as a security boundary.
- **The scripts make no network connections** and run no downloaded or generated code, apart from rollback.ps1, which Remediations.ps1 generates from its own Invoke-Rollback function into the administrators-only state folder.
- **The audit logs are readable by every local user**, because WatchDog runs as the signed-in user. They list the settings that are not in the expected state, so they tell a local attacker which weaknesses exist. They contain no passwords or keys.
- **Fail closed.** A check that cannot be evaluated counts as a failure.
- **Smart App Control and diagnostic data pull in opposite directions.** Smart App Control (SAC) blocks apps that are neither signed by a trusted publisher nor known to Microsoft's cloud reputation service as good, which is an important protection against malicious downloads. Microsoft offers SAC only when optional diagnostic data is turned on; it is unavailable as long as only required diagnostic data is sent. CIS 18.10.16.1 (Level 1), which this baseline follows, allows only "Diagnostic data off" or "Send required diagnostic data" and so excludes optional diagnostic data, and with it SAC. The two are not weighed against each other anywhere:
    - CIS treats data leaving the PC as a security risk, not only a privacy matter. Optional diagnostic data includes app and feature usage, browsing data from Microsoft Edge and more detailed error reports, which can contain parts of a program's memory. CIS allows the required minimum because Microsoft Defender depends on it.
    - Tying SAC to optional diagnostic data is a product decision by Microsoft, not a technical necessity: SAC asks the cloud service about every unknown app, and Microsoft offers it only to users who agreed to share more data.
    - The CIS benchmark has no SAC recommendation at all. It covers settings that can be managed by policy, and SAC cannot be. Organizations get the same protection from App Control for Business, the policy-based allow-listing SAC is built on, which does not need optional diagnostic data. For a stand-alone PC this leaves a gap the benchmark does not address.

    Which matters more depends on the main risk of the PC. Where people install whatever they find, SAC likely protects more than optional diagnostic data costs. On a developer PC, SAC is impractical anyway: it has no exceptions and would block self-built unsigned programs such as WatchDog.exe, and App Control normally runs scripts it does not trust in PowerShell's Constrained Language Mode, which blocks the .NET calls the scripts of this suite use. Where sensitive data is stored on the PC, the CIS setting is the safer default. This baseline keeps the CIS setting where SAC is Off, so SAC stays off there and is not checked by the audit. Turning SAC on means allowing optional diagnostic data (removing the AllowTelemetry policy, then choosing it in Settings > Privacy & security > Diagnostics & feedback), which is a deliberate deviation from CIS 18.10.16.1. Depending on the Windows build, turning SAC on afterwards may also require resetting or reinstalling Windows.

    **A PC where SAC is already On or in Evaluation keeps it.** Microsoft documents optional diagnostic data only as a condition for turning SAC on. Whether turning the data off later disables an active SAC is not documented: user reports suggest SAC stays on, but that is not confirmed, and the AllowTelemetry policy might behave differently from the switch in Settings. If it did disable SAC, rollback.ps1 could not undo it, because restoring the policy does not turn SAC on again (that may need a reset of Windows; after update KB5127648 the switch was reported greyed out on PCs where SAC had been turned off), and Evaluation mode exists only after a fresh installation. Following the rule that a change rollback cannot undo is not made, Remediations.ps1 reads the SAC state (VerifiedAndReputablePolicyState in HKLM\SYSTEM\CurrentControlSet\Control\CI\Policy: 0 Off, 1 On, 2 Evaluation; a missing value counts as Off) and sets AllowTelemetry only when SAC is Off. When SAC is On, in Evaluation or its state cannot be read, it skips the setting and prints why. In the same situation Audit.ps1 skips the Diagnostic Data Level check with that reason ("[SKIP] Diagnostic Data Level — skipped: Smart App Control is On and requires optional diagnostic data ..."), unless the policy already has the expected value, so such a PC gets no hourly toast for a setting the baseline deliberately leaves alone. To apply the CIS setting there anyway, turn SAC off in Windows Security first.
- **A busy Windows does not stall the audit.** The SMBv1 and PowerShell 2.0 checks read Windows optional features through DISM, which answers only when no installation or update holds the servicing lock; it once took 7 minutes while an update was being installed. Audit.ps1 therefore runs each DISM query with a time limit shared by the whole run, 10 minutes in total. A query that does not finish in time fails its check ("could not verify: Windows servicing (DISM) did not answer within 10 minutes ..."), and later DISM queries fail at once, so a busy Windows raises a toast instead of delaying the audit indefinitely. For any other hang, the scheduled task stops after 45 minutes (section 5.2, step 5).
- **File deletion by the task is limited.** The scheduled audit, which runs every hour as LocalService or SYSTEM, deletes only its own logs and temporary files. Remediations.ps1 and rollback.ps1 delete only their own temporary and rollback state files.
- **WatchDog runs with least privilege** in the user's session and only reads one file.
- **The toast is not protected against the signed-in user's own processes.** WatchDog.exe, its scheduled task and the logs cannot be changed without elevation, but the toast is shown in the user's session through a Start menu shortcut and notification settings that belong to that user. A process running as the signed-in user can delete the shortcut, turn the notifications off, dismiss a toast or show one of its own; Windows has no boundary between processes of the same user. Processes of other standard users cannot. The logs in %ProgramData%\SecurityAudit are the trustworthy record; the toast is a convenience.
- **Rollback state is sensitive.** The snapshot and the .inf exports describe the machine's earlier security settings. They are stored in %ProgramData%\SecurityBaseline. Remove them when they are no longer needed, either by rolling back or by deleting them once you no longer need the option to roll back.

## 12. Troubleshooting

When a toast or a log looks wrong, these records show what happened. All can be read without elevation, except where noted.

- **%ProgramData%\SecurityAudit\SecurityAudit.log:** the latest audit, one time-stamped line per check. The header shows when the PowerShell process started and how long it took to open the log; the summary line ("Checks run: ...") shows the totals and the duration. A log without the summary line belongs to a run that was stopped or failed; the time stamps show the last check it reached.
- **%ProgramData%\SecurityAudit\SecurityAudit.previous.log:** the audit before, useful when the latest run has already replaced a log that WatchDog reported.
- **%LOCALAPPDATA%\SecurityAudit\WatchDog.log:** one line per WatchDog run: what it found (finished, unfinished, missing or in use, with the time the log was last written), whether the audit task was running, and whether it showed a toast, or its error. Any program running as the user can change this file, so treat it as a hint and confirm with the records below.
- **Task Scheduler history** (Event Viewer > Applications and Services Logs > Microsoft > Windows > TaskScheduler > Operational, or Get-WinEvent -LogName 'Microsoft-Windows-TaskScheduler/Operational'): when each run of "\Security Configuration Audit" and "\Security Configuration Watchdog" started (event 100) and finished (event 102). A run that ends exactly 45 minutes after it started was stopped by the task's time limit. The audit starts at the same minute of every hour (the minute of the installation), plus a make-up run soon after Windows starts or wakes when a slot was missed.
- **Sleep and wake** (System log, provider Microsoft-Windows-Kernel-Power): event 506 means the PC entered Modern Standby and 507 that it left it (the reason shows, for example, "Lid"). A run that started during a short wake and was then frozen by standby is the usual reason for a run stopped by the time limit; that run is reported once by WatchDog unless a newer run is already running.
- **Remediations.ps1:** its console output, the change report of each run (section 8.3) and Remediations.cmd Analyze (section 9.3, elevated).
